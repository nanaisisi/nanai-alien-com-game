## 2. 領域別詳細技術検討

### 2.1 ヘックス座標・幾何計算 (Hexagonal Coordinate System)

- **対象コード**: `src/map/hex.rs` (`HexCoord`, 軸座標 $q, r$、距離算出、近傍取得、ワールド座標変換)
- **候補クレート**: `hexx` (Bevy親和性の高いヘックス幾何クレート)

#### 2.1.1 比較・評価

- **導入メリット**:
  - `hexx` は豊富なヘックス形状（Pointy / Flat）、回転、レイキャスト、リング・ライン描画アルゴリズムを内包する。
  - Bevy向けプラグインが公式に提供されている。
- **懸念点・デメリット**:
  - 本作の最大の特徴である **「X軸円筒世界（Cylindrical Wrap-around）」** において、`col = q + (r - (r & 1)) / 2` の剰余演算を用いた境界正規化や、最短ラップ距離計算 (`test_wrap_distance`) を常時伴う。
  - `hexx` は平面グリッドを主眼としており、円筒ラップを全近傍探索・幾何計算で透過的に扱うには結局カスタムラッパーが不可欠となる。
  - 現行の `src/map/hex.rs` は約200行とコンパクトであり、Bevy 0.20 の `Reflect`, `Component` に最適化されている。
- **結論・推奨**: **見送り（独自実装維持）**
  - 現行の `HexCoord` 独自実装は十分にテストされており、円筒ラップの振る舞いがコードベース全体（カメラ・メッシュ・入力判定）と緊密に結合しているため、外部クレート化による恩恵よりも抽象化レイヤー増加の摩擦が大きい。

### 2.2 プロシージャル地形ノイズ (Procedural Map Generation)

- **対象コード**: `src/map/generation.rs` (`sample_value_noise`, `cylinder_noise_with_size`, `hash3d`)
- **候補クレート**: `fastnoise-lite`, `noise-rs`

#### 2.2.1 比較・評価

- **導入メリット**:
  - シンプレックスノイズ、パーリンノイズ、Cellular（ボロノイ）ノイズ、フラクタルブラウン運動（fBm）など高品質かつ多様なノイズアルゴリズムを即時利用可能。
  - ドメインワーピング（Domain Warping）等によるリアルな大陸・河川シミュレーションの表現力向上。
- **懸念点・デメリット**:
  - 本作は経度方向の周期的接続のため、$(cx, cy, cz) = (\cos\theta, y, \sin\theta)$ の3D円筒座標系を用いたノイズサンプリングを行っている。
  - 外部クレートを用いる場合でも3D空間上の円筒サンプリング関数を自前で被せる必要があり、現行の `hash3d` + Smoothstep 3Dバリューノイズ（約60行）で既に破綻なく動作している。
- **結論・推奨**: **将来検討（部分統合）**
  - 現状の陸塊・バイオーム・水域生成は完成度が高く安定している。将来的に「プレートテクトニクス断層」「ボロノイ生体鉱床」「動的瘴気フロー」などの高度なプロシージャル表現が必要となった段階で `fastnoise-lite` の採用を検討する。

### 2.3 経路探索・グラフ解析 (Pathfinding & Graph Analysis)

- **対象コード**: `src/unit/interaction.rs` (`update_reachable_tiles` 等), 将来の動脈インフラ・水域BFS
- **候補クレート**: `pathfinding`, `petgraph`

#### 2.3.1 比較・評価

- **導入メリット**:
  - `pathfinding` は Rust 界で極めて実績のあるアルゴリズム集であり、A\*（A-star）、Dijkstra、IDDFS、Fringe Search などを汎用クロージャで提供。
  - 現在 `update_reachable_tiles` 内で自前実装されている BFS は移動力範囲の全探索に留まっているが、ユニットの「目的地指定長距離移動」「ZOC（敵支配域）回避」「渡河・運河ペナルティ」「道路動脈優先」を考慮した最適経路探索が必要となる。
  - `petgraph` はインフラ動脈（鉄道網・送電線・パイプライン）の切断検知（Biconnected Components / アーティキュレーションポイント）や最大流・ボトルネック解析に極めて強力。
- **懸念点・デメリット**:
  - 円筒世界ラップを考慮した隣接ノード展開関数（`neighbors_with_width`）を探索器に渡す設計が必要（`pathfinding` のAPIは状態遷移関数を渡すスタイルであるため相性は非常に良い）。
- **結論・推奨**: **即時推奨（`pathfinding` の導入）**
  - 単純なBFSから本格的なターン制戦略A\*経路探索へ移行するにあたり、自前でヒューリスティック関数付きプライオリティキューを再実装するより、`pathfinding` クレートを導入して隣接コスト計算に集中する方が保守性・信頼性が大幅に向上する。

### 2.4 データシリアライズ・外部定義ファイル管理 (Serialization & Data Pipeline)

- **対象コード**: `assets/data/factions.csv`, `assets/data/city_names.csv`, 将来のモジュール・兵装定義
- **候補クレート**: `serde`, `csv`, `ron` (Rusty Object Notation)

#### 2.4.1 比較・評価

- **導入メリット**:
  - 現在 `assets/data/` に配置されているCSVファイル（都市名全192件・勢力基本データ）は、まだコード側で動的ロードされず一部ハードコードされている。
  - `csv` + `serde` を導入することで、起動時またはアセットローダー経由でCSVを構造体へ一括デシリアライズ可能になり、データ追加やMod制作が容易になる。
  - 兵装カタログや技術ツリーなどの階層型仕様は、Rust型と1対1対応する `ron` または `serde_json` で定義することで、コードを汚さずに膨大なスペックを外出しできる。
- **懸念点・デメリット**:
  - Bevy内部でも `serde` は多用されているため、依存衝突リスクは皆無。
- **結論・推奨**: **即時推奨（`csv` + `serde` の導入）**
  - 勢力名・都市名マスター、初期スタートアップアセットの外部ファイル化を完成させるために最優先で利用すべきである。

### 2.5 UI・開発者ツール (UI & Debug Tooling)

- **対象コード**: `src/ui/debug_console/`, 将来のドクトリン・ステアリングUI、兵器インスペクター
- **候補クレート**: `bevy_egui`

#### 2.5.1 比較・評価

- **導入メリット**:
  - `bevy_egui` は即時モード（Immediate Mode）GUIであり、デバッグコンソール、パラメータ調整スライダー、ECSインスペクターを極めて短時間・低コード量で構築可能。
- **懸念点・デメリット**:
  - 本作はゲーム本編のUIに Bevy 0.20 の新機能（`Val::Em` / `Rem`, `FixedNode`, Weak Ordering, Picking）を採用し、テーマカラー・フォント（UDEV Gothic NF）による統一されたSFデザインを確立している。
  - ゲーム本編HUDやメニューに `bevy_egui` を混在させると、UIスケーリングやデザインの二重管理が発生し、体験が損なわれる。
- **結論・推奨**: **限定推奨（デバッグ・開発者向けツールに限定）**
  - ゲーム本編の操作・ステアリングUIは現行の Bevy 0.20 公式UIシステムを堅持する。
  - 開発用の内部状態監視ウィンドウ、ノイズ・バイオーム調整ツール、AI挙動可視化などのデバッグ用途に限定して `bevy_egui` を活用することは合理的である。

### 2.6 決定論的乱数・シード管理 (Deterministic RNG)

- **対象コード**: `src/map/generation.rs`, 将来の戦闘解決（損耗・命中ダイス）
- **候補クレート**: `fastrand`, `rand_chacha`

#### 2.6.1 比較・評価

- **導入メリット**:
  - 現在マップ生成ではシードを用いた自前の算術ハッシュ (`hash3d`) を使用しているが、戦闘解決の確率ダイスやイベントトリガーにおいて、決定論的（シード値から完全に再現可能）かつ高速な疑似乱数生成器が求められる。
  - `fastrand` は軽量・高速（Wasmやマルチプラットフォームで依存ゼロ）、`rand_chacha` は暗号学的かつプラットフォーム非依存の完全決定論的再現性を誇る。
- **懸念点・デメリット**:
  - 標準ライブラリの乱数は存在しないため、ゲームプレイの再現性（リプレイ、セーブ＆ロードでの同一結果、マルチプレイ同期）を担保するには外部クレートが事実上必須。
- **結論・推奨**: **即時推奨（`fastrand` または Bevy内蔵機能）**
  - Bevy自身も内部で `fastrand` や `rand` を依存として持っているため、プロジェクトの直接依存に `fastrand` を明示追加し、ゲームシミュレーションの決定論性を確立することを推奨する。

### 2.7 自律AI・集団合意アーキテクチャ (Autonomous AI & Consensus Architecture)

- **対象コード**: 将来予定のエイリアン生態系（`ALIEN_ECOLOGY_AND_NEST_SYSTEM.md`）、国家自律行動
- **候補クレート**: `big-brain` (ユーティリティAI), `seldom_state` (ステートマシン)

#### 2.7.1 比較・評価

- **導入メリット**:
  - エイリアン巣窟のライフサイクル（休眠→活性→繁殖→暴走スウォーム）や、部隊の兵站ステートマシン（Normal→Strained→Critical→Exhausted）の遷移ロジックを宣言的に記述可能。
- **懸念点・デメリット**:
  - ドキュメント `concept_autonomous_control_and_atmospheric_consensus.md` で規定されている通り、本作の自律AIは「社会の空気・暗黙の合意」を模倣する超軽量ルールベース判定＋システム間プロパティ平滑化を設計方針としている。
  - 過度に複雑な行動木（Behavior Tree）や重厚なAIフレームワークを導入すると、ECS本来の単純なイテレーション性能や並列性が阻害される恐れがある。
- **結論・推奨**: **将来検討（ステートマシン `seldom_state` のみ部分評価）**
  - 複雑な行動フレームワークの全面導入は見送り、まずは Bevy標準のコンポーネント＋システムによるルールベース実装を進め、状態遷移が複雑化した箇所にのみ軽量ステートマシンの導入を検討する。

## 3. 導入ロードマップと優先度

1. **優先度 高（直近で導入を推奨）**:
   - `serde` + `csv`: `assets/data/` 内の勢力・都市名CSVデータの読み込み完全自動化。
   - `pathfinding`: ユニット移動のA\*経路探索・ZOC回避・運河/渡河ペナルティの正確な計算。
   - `fastrand`: 戦闘解決・イベント判定における決定論的乱数シミュレーションの確立。
2. **優先度 中（開発効率向上のため状況に応じて導入）**:
   - `bevy_egui`: 開発時専用のパラメータチューナー・デバッグ監視コンソール。
   - `ron`: 複雑な技術ツリー（Tech Web）および兵器モジュールカタログの外部定義化。
3. **優先度 低 / 見送り（独自実装維持）**:
   - `hexx`: 円筒世界ラップとの親和性・現行コードの洗練度から独自実装を継続。
   - `big-brain`: ルールベース合意力学方針に基づき標準ECSで十分対応可能。
