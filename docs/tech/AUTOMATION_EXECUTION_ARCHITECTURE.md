# 自動化システム実行順序・実装アーキテクチャ仕様書

本ドキュメントは、本作における自動化システム（内政・兵站・軍備調達・方面軍AI等）とプレイヤー操作の**実行順序の決定論的ルール**および**Bevy ECSにおける実装アーキテクチャ**を定義する技術仕様書である。

---

## 1. 設計原則

1. **プレイヤー優先（Override First）**
   - プレイヤーが手動で操作・指定した対象（移動済みユニット、手動ロックされたモジュールや区画、優先補給指定など）を自動化AIが上書きしてはならない。
2. **操作フェーズとターン解決フェーズの分離**
   - プレイヤーが操作している最中に自動化AIを裏で動かさない。資源や部隊が勝手に動いてプレイヤーの計画を狂わせるストレスを防ぐため、自動化は**ターン終了時（`AdvanceTurnMessage` 発火後）**に一括で解決する。
3. **上流→下流の決定論的パイプライン**
   - 自動化ドメイン間には明確な依存関係が存在するため、実行順序を固定パイプラインとして定義し、毎ターン同じ順序で解決する。

---

## 2. 意思反映の限界と手動介入の設計方針

### 2.1 基本方針：「手動100点 vs 自動85〜90点」（ノーペナルティ）

- 手動操作に枠制限やペナルティを設けてプレイヤーの自由を奪わない。
- 「自動化しても十分勝てる（85〜90点）」精度とバランスを確保することで、勝つために全軍を手動操作するマイクロマネジメント地獄を防ぐ。
- プレイヤーは「楽しいところ・勝負所だけ手動（100点）、面倒な裏方や別正面は自動（85〜90点）」を自由に選択できる。

### 2.2 自動化への意思反映の限界ライン

- 自動化AIに伝える意思は、**「目的（防衛・進撃・牽制）」**と**「許容リスク（損耗回避・標準・損耗覚悟）」**の2軸までに留める。
- 囮・捨て駒、短期決戦の博打、変則プレイなどの細かい戦術的意図は自動化に翻訳しようとせず、手動操作の領分とする。

### 2.3 極端なマイクロ格差（40点 vs 100点）のルール側での防止

- 敵を嬲って経験値を稼ぐようなメタ的抜け道は、弾薬消費・部品摩耗・経験値（実戦データ）の逓減によってルール側からマイルドにし、正攻法の自動化AIとプレイヤーのギャップを抑える。

---

## 3. ターン内の全体実行フロー

1ターンは以下の3フェーズで構成される。

1. **ターン開始（認知フェーズ）**
   - 視界・偵察情報の更新、インスペクション情報の集計、現場承認トレイ（Field Mods等）の通知生成。
   - プレイヤーが現状を把握できる状態で操作権を渡す。
2. **プレイヤー操作フェーズ（手動入力）**
   - ユニット移動、手動建設、国家指針・介入度（Level 0〜3）の変更、優先補給・モジュール固定などの設定。
   - この間は自動化AIを実行しない（必要であれば次ターンの自動化予定をプレビュー表示するに留める）。
3. **ターン解決フェーズ（`AdvanceTurnMessage` 発火後）**
   - プレイヤーが手動で動かした部隊やロックした領域を除外したうえで、上流から下流へ順番に自動化を実行する。

---

## 4. ターン解決パイプラインの詳細順序

`AdvanceTurnMessage` 受信後、以下の7段階の順序で処理を実行する。

| 順序 | ステージ名 | 主な責務 | 主な入力・参照 |
| :--- | :--- | :--- | :--- |
| 1 | `UpdateStance` | 国家指針（思想・好戦性・友好性・孤立性）の実効値を目標値へ近づける（移行ラグ更新） | プレイヤー設定目標値、現行実効値 |
| 2 | `Economy` | 生産・維持費を確定し、余剰資源でサブタイルの自律発展・インフラ投資を実行 | 国家指針、タイル状態、手動ロック |
| 3 | `Logistics` | 確定したインフラ網でサプライチェーン経路探索を行い、品質補正・経験値を伝播 | インフラ網、拠点在庫、優先補給フラグ |
| 4 | `Procurement` | 資源と補給線に基づき、欠品補充・代替モジュール選定・弾薬口径平準化を実行 | 調達ドクトリン、類似性マトリクス、在庫 |
| 5 | `MilitaryAuto` | 委任中（Level 0〜2）かつ今ターン未行動の部隊を移動・防衛配置 | 方面軍指針、作戦ベクトル、未行動フラグ |
| 6 | `NpcAndAlien` | NPC国家・エイリアンの行動および戦闘解決（Auto-Resolve等）を実行 | 各勢力AI状態、接触ユニット |
| 7 | `FinalizeTurn` | ターン数加算、次ターン用の自動化サマリー（`AutomationLog`）集計・フラグ初期化 | 各ステージの実行ログ |

---

## 5. Bevy ECS 実装アーキテクチャ

### 5.1 `TurnResolutionSet` による実行順序の型レベル固定

[src/turn.rs](../../src/turn.rs) を中心に、ターン解決用の `SystemSet` を `.chain()` で直列化する。各ドメインのプラグインは自身のシステムを該当セットに登録するだけで、依存順序が保証される。

```rust
#[derive(SystemSet, Debug, Clone, PartialEq, Eq, Hash)]
pub enum TurnResolutionSet {
    UpdateStance,  // 1. 国家指針・移行ラグ
    Economy,       // 2. 内政・資源・都市発展
    Logistics,     // 3. 兵站・サプライチェーン
    Procurement,   // 4. 軍備・兵器調達
    MilitaryAuto,  // 5. 方面軍AI
    NpcAndAlien,   // 6. NPC・エイリアン・戦闘
    FinalizeTurn,  // 7. ターン加算・UIサマリー生成
}
```

### 5.2 コマンド／意図（Intent）層の統一

自動化AIが `FactionResources` や `Unit` コンポーネントを直接書き換えるのではなく、**プレイヤー操作と同じコマンド（例: `OrderMove`, `OrderBuild`, `AllocateSupply`）を発行する**構造とする。

- **メリット1**: 資源不足や移動範囲外などのルール検証を1箇所に集約できる。
- **メリット2**: プレイヤー操作とAI操作が同じ資源を取り合う競合バグを防げる。

### 5.3 介入度と競合防止フラグ

ドメインやエンティティごとに以下の制御情報を持たせ、自動化システムはクエリ段階で対象を絞り込む。

- **介入度（Escalation Level）**: `FullAuto`（Level 0） / `Guided`（Level 1〜2） / `ManualOnly`（Level 3）
- **競合防止フラグ**: `LockedByPlayer`（モジュール固定・区画保護等）、`ActedThisTurn`（今ターン手動行動済み）

### 5.4 `AutomationLog` による透明性確保

自動化がブラックボックス化すると「バグで資源が減ったのか、AIが消費したのか」が判別できなくなる。自動化がコマンドを実行するたびに `AutomationLog`（例：「第3機甲戦闘団へ代替モジュールを補充」）を記録し、UIのインスペクションパネルやターン報告へ出力できる構造を最初から組み込む。

## 6. 段階的実装ロードマップ

| フェーズ | 実装内容 | 検証ポイント |
| :--- | :--- | :--- |
| **Step 1: パイプライン基盤** | `TurnResolutionSet` の定義と `AutomationLog` リソースの導入 | `AdvanceTurnMessage` で全セットが定義順に実行されること |
| **Step 2: 単一ドメイン検証** | 依存の少ない1ドメイン（内政の自動配分、または兵站の補給充足）を実装 | 自動実行の結果が `AutomationLog` とUIに正しく反映されること |
| **Step 3: 競合防止の検証** | `LockedByPlayer` / `ActedThisTurn` / 優先補給フラグの導入 | プレイヤーの手動操作やロックをAIが上書きしないこと |
| **Step 4: 他ドメイン拡張** | 兵器調達・方面軍AI・NPC/エイリアン処理を順次パイプラインへ接続 | 上流→下流の依存関係が破綻せずターンが完走すること |
